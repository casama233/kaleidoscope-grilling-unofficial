# First bottle placement hand selection

The [official BlockComponentPlayerPlaceBeforeEvent](https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/blockcomponentplayerplacebeforeevent?view=minecraft-bedrock-stable) provides no hand or itemStack. All 67 bottle IDs place the same block route, so its permutation cannot distinguish two differently named or filled bottles. Offhand eligibility alone therefore cannot establish safe first placement.

The native `scheduleNativeBottlePlacement` entry cancels native placement before examining both hands through strict, read-only `captureWritableHand` snapshots. Exactly one bottle candidate is required. Zero/two candidates, an unreadable hand or an inconsistent captured hand cause an immediate return without consuming either stack or creating storage. Both-bottle ambiguity is rejected even when IDs or metadata differ; no main-hand priority is invented.

For the unique candidate, existing before-safe interaction capture retains native clones. The deferred callback retains its original metadata, selected-slot, dimension, reach, target, support and storage checks. Its existing transaction writes a clone of the original bottle and debits the captured hand, with the same rollback/retirement behavior. Restricted getters remain deferred; no new ItemStack ID or reconstructed metadata path is introduced.

Pinned [Java SeasoningBottleBlock](https://github.com/breezeth-CN/KaleidoscopeGrilling/blob/9a1acdab27698457bec16c9362678e574895a28c/neoforge-1.21.1/src/main/java/cn/breezeth/kaleidoscope_grilling/seasoning/SeasoningBottleBlock.java) uses the engine-provided stack in setPlacedBy. Its pickupOne explicitly returns the bottle to MAIN_HAND. [PENDING](https://github.com/breezeth-CN/KaleidoscopeGrilling/blob/9a1acdab27698457bec16c9362678e574895a28c/neoforge-1.21.1/src/main/java/cn/breezeth/kaleidoscope_grilling/seasoning/PendingSeasoningItem.java) passes the supplied hand to startUsingItem and inherits BlockItem placement. The Java pickup rule does not make placement main-only. This change leaves all pickup, eating and Tavern handlers untouched.

Source/API-double regressions cover unique offhand EMPTY/PENDING/SPECIAL first placement, pickup/replace metadata roundtrips, empty/nonbottle main hand, before-phase restricted getter rejection with zero reads, two differing or identical bottles cancelled without mutation, queued metadata changes in either hand, failed inventory reads and offhand writes failing before/after mutation with rollback. The storage fixture now models an actually empty independent offhand rather than aliasing both requested hands to one main stack.

These tests are not native GUI acceptance. Explicit by-hand pickup calls in doubles do not establish that native UI can select the same pickup hand. No API-forced equipment, client control, deployment or release is part of this source change.

## Script interaction supplement

The owner's private log-only comparison on Bedrock 1.26.52.3 established that the same PENDING bottle placed through the main-hand native callback, but GUI-equipped offhand Use produced 18 beforeInteract events with an empty event item and no placement entry or itemUse. This identifies a missing native dispatch on this client and bottle path, not a return inside the placement function or a claim about all Bedrock versions.

`tryScheduleOffhandBottleInteraction` now handles that real beforeInteract path. It requires an uncancelled initial press, an empty event item, strictly readable empty main hand, one supported offhand bottle, the Up face, one of 24 exact vanilla inert full-cube support IDs and exactly minecraft:air above. The support allowlist is deliberately conservative: containers, workstations, partial blocks and unrecognized/custom surfaces retain their normal interaction. Nonempty main hands remain on their existing paths; two-bottle native placement remains fail-closed. Successful admission cancels the original interaction event and passes the real offhand intent directly to the shared transaction, without inventing a native placement event or moving equipment.

`queueBottlePlacement` is shared by both entries. A pending claim keyed by stable player ID deduplicates callbacks until the deferred action completes, including failed actions and rollback. Hold/repeat events are ignored by the supplement; a later initial press can retry after completion. Claim cleanup runs in finally and also on scheduling failure. Selected-slot changes now invalidate offhand placement as well as main-hand placement. Original metadata, both hands, dimension, mode, reach, target, support, storage ownership and debit/rollback checks remain in the same transaction.

The canonical gate now includes the actual beforeInteract subscription regressions. They cover EMPTY/PENDING/SPECIAL exact metadata; PENDING eight materials; main-hand pickup and offhand replace; JSON serialization of saved dynamic properties/helper inventory and module reload; excluded surfaces and occupied targets; cancelled, repeat and invalid-face events; queued item/metadata/slot/location changes; unresolved saved projection; both entry orders with survival/creative; wrapper-independent deduplication; write rejection before/after mutation and retry; main-hand regression. Serialization/API doubles are not Minecraft disk persistence evidence.

Pending owner acceptance: GUI offhand placement on stone with empty main, short/held/repeated Use, empty-main pickup then replace, save/exit/reload, excluded interactive supports, occupied targets and main-hand/two-bottle regression. This feature is a script interaction supplement, not native offhand block_placer support. Release identity/freeze and integration remain the owner's separate canonical candidate step.
