# ONE / THREE representative renderer and PR124 final-head comparison

This follow-up to `05f793186e448a9d82df0702a6e2408d59c7deda` activates the source-derived renderer for cooked fish (ONE, 90 native ticks) and cooked ender pearl (THREE, 100 native ticks). It is an unfrozen source candidate. No pack identity, item definition, recipe, effect, metadata serializer or completion transaction changes.

## Runtime wiring

The normal bite-stage geometry, textures and controller remain intact. Each representative's existing attachable gains a second render controller and a mesh converted from the exact Java `SkewerEatingPiece` resolver. Cooked source texture pixels and per-face UV rotations are preserved. The helper mesh binds to the other native item slot using `query.item_slot_to_bone_name`; it creates no ItemStack and writes no offhand equipment.

Both arms and both item sockets receive the pinned Java ONE/THREE curves. Each socket handles its own wide/slim shift. A piece's child translation includes the source scale before the mesh-center translation; omitting that scale changed its origin by nearly eight model units in hidden frames and was caught by the committed-runtime matrix regression. ONE's visibility remains the exact source step at 1.16667 seconds. THREE retains its authored scale window. The animation lengths are 4.5 and 5 seconds respectively and use the existing captured native countdown clock.

The script admission and all client draw gates require an empty helper hand. An occupied helper hand falls back to the existing renderer, preserving its stack and presentation. Local item/profile/hand/use/posture gates mask packet-stale projections, canceled use, changed items and TP views. Both arms are exposed only inside that scoped first-person projection. The piece is hidden while idle and in third person. The 40-attachable FP/TP separation and replicated observer bite clock remain unchanged.

Shared integration paths are `behavior_pack/scripts/main.js` (one admission condition), `resource_pack/animations/java_eating_player.animation.json`, and `resource_pack/render_controllers/java_eating_player.render_controllers.json`. No `behavior_pack/entities/player.json`, RP player definition or new shared property is introduced. Item eligibility, the item animation table, two attachables, two piece models/textures and the new piece controller are also required runtime assets. The generator reproduces those assets; it is not the feature's only deliverable.

The [official slot-bone query](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/molangreference/examples/molangconcepts/queryfunctions/query_item_slot_to_bone_name?view=minecraft-bedrock-stable) describes mapped slot resolution, and the [official equipped-item query](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/molangreference/examples/molangconcepts/queryfunctions/query_is_item_equipped?view=minecraft-bedrock-stable) supports main/off hand arguments. Cross-slot binding on a single native attachable is an implementation inference from that interface and still requires a real-client test; the static tests cannot certify native rig dispatch.

## Verification boundaries

The renderer regression reconstructs both committed arm/socket channels and both meshes across profiles, hands, wide/slim rigs and every generated sample. It compares the full composed result with the pinned Java renderer matrices, rather than merely checking generator output. It also checks exact representative geometry, source texture pixels, item eligibility, piece RC references and cancellation/TP/item/profile/other-hand visibility gates.

Production subscriber/API-double tests cover native completion, cancellation, repeated use, duplicate callbacks, swapped item/slot/metadata and the four representative profile/hand combinations with empty and occupied helpers. Render audits retain the 150 main bite-stage geometry checks and add the two independent pieces; intentionally hidden idle pieces are checked by their dedicated use renderer contract. These are source/static/API-double results, not native-player recordings.

Real-client acceptance is required for helper-slot binding, FOV/skin/camera calibration, UV rendering, both use hands, native timer queries and cancellation transitions. BDS, compiled-pack admission and a true second observer remain separate owner-run gates. Only these two fixed representatives are activated. Raw fish, caterpillar, additional THREE candidates, secret/mysterious/dark ingredient pieces and arbitrary foreign ingredient meshes are not activated. Occupied-helper dual rendering and Java per-use native 90/100 randomness are not implemented by this no-ID-swap branch.
